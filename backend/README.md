# NexaPilot Backend (Phases 1-4 — Foundation + Blockchain + AI + Safety Layer)

FastAPI + SQLAlchemy + Alembic + web3.py + Claude backend for NexaPilot,
targeting Supabase PostgreSQL and Monad. Frontend (Phase 5+) is still not
part of this repo — see the project's phased plan.

## What's here

- Versioned API under `/api/v1`
- Health check with live DB **and** Monad RPC connectivity checks
- Wallet-based "connect" auth that issues a JWT (see security note below)
- SQLAlchemy models for `users`, `wallets`, `policies`, `transactions`,
  `activities`
- Alembic migrations (single source of truth for the DB URL: `app.core.config.settings`)
- Centralized error handling — every error response has the shape
  `{"error": {"code": "...", "message": "...", "details": ...}}`
- **Blockchain layer** (`app/blockchain/`) under `/api/v1/blockchain/*`:
  wallet balance reads (native + in-contract vault balance), unsigned
  transaction construction against the deployed `NexaPilotExecutor`
  contract (see `../contracts/`), deterministic pre-flight validation,
  broadcast-and-relay of already-signed transactions, and on-chain
  verification that updates the `transactions`/`activities` tables. The
  backend never signs a production transaction — see "Auth & signing
  scope" below.
- **AI layer** (`app/ai/`) under `POST /api/v1/ai/query`: turns a
  natural-language DeFi request into a Pydantic-validated structured
  action using Claude with a bounded tool-use loop. See "AI layer" below.
- **Safety layer** (`app/risk/`, `app/policy_engine/`) under
  `/api/v1/risk/*` and `/api/v1/policy/*`: a deterministic Risk Engine and
  Policy Engine that every Claude-generated `TRANSACTION_PLAN` is run
  through before it's ever eligible for execution. Neither is AI — same
  inputs always produce the same output. See "Safety layer" below.

## Setup

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt   # includes requirements.txt + test deps

cp .env.example .env
# edit .env: set DATABASE_URL to your Supabase Postgres connection string
# (Session pooler, port 5432) and a real JWT_SECRET.

alembic upgrade head          # creates all tables
uvicorn app.main:app --reload # http://127.0.0.1:8000
```

Interactive API docs: `http://127.0.0.1:8000/docs`

## Blockchain layer setup

The blockchain layer reads the deployed contract's address + ABI from
`../contracts/deployments/<BLOCKCHAIN_NETWORK>.json` — that file is
generated by `contracts/script/deploy.sh` and is the single source of
truth (never hand-copy an address into `.env`).

**Local devnet (default, for development/testing):**

```bash
anvil --chain-id 10143 &                     # a devnet pinned to Monad's real chain id
cd ../contracts
DEPLOYER_PRIVATE_KEY=0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80 \
  ./script/deploy.sh local                   # writes deployments/local.json
cd ../backend
# .env: BLOCKCHAIN_NETWORK=local, MONAD_RPC_URL=http://127.0.0.1:8545 (already the default)
uvicorn app.main:app --reload
```

**Real Monad testnet:** deploy per `contracts/README.md`, then set
`BLOCKCHAIN_NETWORK=monad_testnet` and `MONAD_RPC_URL=https://testnet-rpc.monad.xyz`
in `.env`. No code changes needed either way.

Prove the full flow (backend → contract → tx → verification → DB) end to
end with the server running:

```bash
python scripts/dev_e2e_blockchain_test.py
```

This deposits, executes against an allow-listed test protocol, and
withdraws — using a local anvil dev key to sign, standing in for what a
real connected wallet (Privy/wagmi, added in Phase 5) will do. It is not
part of the API; it's the Phase 2 proof harness.

## AI layer

`POST /api/v1/ai/query` (auth required) takes `{"message": "..."}` and
returns a validated `NexaPilotAIAction` — never anything Claude produces
unchecked. The flow, entirely in `app/ai/`:

1. `client.py` builds the Anthropic client from `ANTHROPIC_API_KEY` (set
   it in `.env`; `claude_model`/`ai_max_tokens`/`ai_max_tool_iterations`/
   `ai_max_output_retries` are also configurable there).
2. `prompts.py` holds the NexaPilot system prompt: what Claude's role is,
   the supported intents (`EXPLANATION`, `PORTFOLIO_ANALYSIS`,
   `OPPORTUNITY_DISCOVERY`, `COMPARISON`, `TRANSACTION_PLAN`), and an
   explicit instruction that Claude never executes anything — it only
   proposes.
3. `tools.py` gives Claude four **read-only** tools backed by the real
   Phase 2 blockchain service (`get_wallet_balance`, `get_network_status`,
   `get_user_policy`, `list_yield_opportunities`) plus one mandatory
   `submit_nexapilot_action` tool that is the *only* way Claude can end
   the turn (`tool_choice={"type": "any"}` forces a tool call every turn).
   There is no `execute`/`send`/`sign`/`withdraw`/`transfer` tool for
   Claude to call — `test_only_read_only_tools_are_dispatchable` in
   `tests/test_ai.py` asserts that directly.
4. `service.py`'s `run_ai_query()` runs the loop: Claude may call the
   read-only tools any number of times, then must call
   `submit_nexapilot_action`; that input is validated against
   `app.schemas.ai.NexaPilotAIAction` (Pydantic). An invalid submission is
   handed back to Claude as a tool error so it can self-correct, bounded
   by `ai_max_output_retries`. Only a validated action is ever returned.
5. `app/api/v1/endpoints/ai.py` decides what to persist: a
   `TRANSACTION_PLAN` action creates a `Transaction` row in **`PENDING`**
   status (a stored proposal only — not risk/policy-checked, not built
   into an unsigned tx, not awaiting approval yet; that's Phase 4's job)
   plus a `RECOMMENDATION` activity row. Any other intent creates only the
   activity row — no transaction.

**Testing without a real API key.** `tests/test_ai.py` uses a scripted
fake Anthropic client (`ScriptedAnthropicClient`) built from the real SDK's
own Pydantic types (`anthropic.types.Message`/`ToolUseBlock`/`TextBlock`)
that replays a fixed sequence of responses — no network call, no cost,
fully deterministic. It exercises the full loop end to end (tool calls
before the final answer, the self-correction retry on an invalid
submission, retries exhausted, no-tool-call error, and the HTTP-level
`PENDING` transaction + activity persistence) plus the "only read-only
tools exist" safety property. This was a deliberate choice for this
sandbox, which has no `ANTHROPIC_API_KEY` available — set a real key in
`.env` and the exact same code path runs unchanged against the live API;
nothing about `app/ai/` differs between the two.

## Safety layer

Every `TRANSACTION_PLAN` Claude produces (via `/api/v1/ai/query`) is run
through two deterministic, non-AI checks before its `Transaction` row
lands on a final status — "AI recommendations are never trusted directly"
(project rule) enforced in code, not just in the prompt:

1. **Risk Engine** (`app/risk/engine.py`, `assess_risk()`). A pure
   function — no I/O, no database, no AI — that scores an action
   LOW/MEDIUM/HIGH from six fixed, weighted factors: protocol risk
   category, liquidity, volatility, illustrative APY, amount concentration
   (relative to the wallet's live balance when available, an absolute
   scale otherwise), and operation type (an `execute` call to an external
   contract scores higher than the vault's own `deposit`/`withdraw`).
   Every factor's raw value, score, weight, and contribution is returned
   alongside the verdict (`RiskAssessment.factors`), so a HIGH rating is
   always explainable, never a black box. The protocol registry
   (`app/risk/protocol_data.py`) is built from the same demo opportunity
   dataset Claude reads (`app/ai/opportunities.py`), so the two can never
   disagree about a protocol's risk category. Claude's own `risk_notes`
   field is advisory text for the user only — this module never reads it.

2. **Policy Engine** (`app/policy_engine/engine.py`, `evaluate_policy()`).
   Also a pure function (given the day's already-committed spend as a
   plain argument) that checks the action, plus the Risk Engine's verdict,
   against the user's own stored `Policy` row (`/api/v1/policies/me`):
   max transaction amount, daily limit (summed across the user's own
   `AWAITING_APPROVAL`/`APPROVED`/`SUBMITTED`/`CONFIRMED` transactions
   created since UTC midnight — a merely-proposed or already-rejected
   transaction never counts against it), allowed protocols, allowed
   actions (both: an empty list configured means "no restriction", not
   "nothing allowed"), and max risk level. Every rule runs independently
   and every result is returned (`PolicyDecision.checks`), so a rejection
   always lists every reason, not just the first one hit.

`determine_transaction_status()` is the single place that turns a
`PolicyDecision` into the `Transaction.status` enum value — reused
identically by the AI flow and the standalone endpoint below so they can
never disagree:

| Outcome | `Transaction.status` |
|---|---|
| Failed the `max_risk_level` policy rule | `RISK_REJECTED` |
| Failed any other policy rule (amount/daily-limit/protocol/action) | `POLICY_REJECTED` |
| Passed, and the policy requires approval | `AWAITING_APPROVAL` |
| Passed, and the policy does not require approval | `APPROVED` |

`Transaction.risk_level`, `risk_explanation`, and `policy_decision`
(all Phase 1 columns, populated for the first time here) hold the full
audit trail for every proposed transaction — visible via
`GET /api/v1/transactions/{id}`.

**Standalone endpoints** (independent of Claude, useful for testing or a
future frontend "what would happen if I did this?" preview):

- `POST /api/v1/risk/assess` — score a hypothetical action
  (`operation`, `amount`, `protocol`, `action_type`) and get back a
  `RiskAssessment`.
- `POST /api/v1/policy/evaluate` — runs the exact same
  Risk Check → Policy Check → PASS/REJECT pipeline the AI flow uses, for a
  hypothetical action, returning the risk verdict, the full
  `PolicyDecision`, and the `final_status` it would resolve to.
- `GET /api/v1/policy/usage` — how much of today's daily limit is already
  committed, and how much headroom remains.

`tests/test_risk_policy.py` covers all of this: pure unit tests of both
engines (including that they're genuinely deterministic — same inputs,
same outputs, called twice), the standalone endpoints, and full
end-to-end scenarios through `/api/v1/ai/query` proving a real
Claude-generated `TRANSACTION_PLAN` gets `POLICY_REJECTED` for exceeding
the max amount, `RISK_REJECTED` for exceeding the configured max risk
level, and `POLICY_REJECTED` on a second call once the daily limit is
already spent — all using the same scripted fake Anthropic client as
`tests/test_ai.py`, so no live Claude API call is needed to prove any of
it.

## Supabase connection notes

- Use the **Session pooler** connection string (port 5432) for
  `DATABASE_URL` under normal operation.
- If you instead use the **Transaction pooler** (port 6543, pgbouncer
  transaction mode), set `DB_USE_NULLPOOL=true` in `.env` — that mode is
  incompatible with SQLAlchemy's own connection pooling.

## Running tests

Tests run against a real local Postgres database (not SQLite), since the
models use Postgres-appropriate types end to end.

```bash
createdb nexapilot_test   # once, if it doesn't exist
pytest -q
```

Override the test DB with `NEXAPILOT_TEST_DATABASE_URL` if needed. Each
test runs inside a transaction that's rolled back afterward, so tests
don't leak data into each other; the schema itself is created once per
test session and dropped at the end. `ANTHROPIC_API_KEY` is not required
to run the suite — `tests/test_ai.py` and `tests/test_risk_policy.py` use
a scripted fake client (see "AI layer" above). Currently 49 tests pass
(11 Phase 1, 7 Phase 2, 8 Phase 3, 23 Phase 4).

## Auth & signing scope — what's real, what's deferred

`POST /api/v1/auth/connect` trusts the wallet address the client sends —
it does **not** yet verify a wallet signature. Wallet ownership is meant
to be proven client-side by Privy in the frontend/wallet-integration
phase; wiring real signature verification into this endpoint is a TODO
called out directly in `app/api/v1/endpoints/auth.py`. Until that lands,
this endpoint should not be treated as proof of wallet ownership — it
only establishes a backend session for an address the frontend claims is
connected.

The blockchain layer follows the same non-custodial principle: `/prepare`
returns an **unsigned** transaction; the backend has no private key for
any user and never signs on their behalf. `/submit` only relays a
transaction the caller's own wallet already signed. In production
(Phase 5+) that signer is the user's Privy/wagmi wallet in the browser;
today, `scripts/dev_e2e_blockchain_test.py` plays that role with a local
anvil dev key purely to prove the flow — that script is test tooling, not
part of the API.

## Why this wasn't tested against the real Monad testnet from here

This backend was built and its blockchain layer fully exercised (unit +
integration tests, a full deposit→execute→withdraw→verify run) from an
Anthropic cloud sandbox whose outbound network is allow-listed to package
registries and GitHub only — Monad's RPC endpoints aren't reachable from
here. Everything was instead proven against a local anvil devnet pinned to
Monad's real chain id (`10143`) — same ABI, same JSON-RPC surface, real
mined transactions. See `contracts/README.md` for the one-command real
deploy; nothing about the backend code changes to point it at real Monad
testnet, only `.env`'s `BLOCKCHAIN_NETWORK`/`MONAD_RPC_URL`.

## Project structure

```
app/
  core/         settings, JWT, centralized exceptions, logging config
  db/           SQLAlchemy engine/session/Base
  models/       ORM models (users, wallets, policies, transactions, activities)
  schemas/      Pydantic request/response models
  blockchain/   Web3 client, contract deployment loader, tx validation,
                balance/tx/verification service (Phase 2)
  ai/           Claude client, system prompt, read-only tools, agentic
                tool-use loop + output validation (Phase 3)
  risk/         deterministic Risk Engine + protocol registry (Phase 4)
  policy_engine/ deterministic Policy Engine (Phase 4)
  api/v1/       versioned routers + endpoints
  main.py       FastAPI app factory
alembic/        migrations (env.py reads DB URL from app.core.config)
tests/          pytest suite (real Postgres + real local-devnet Monad RPC +
                scripted fake Anthropic client)
scripts/        dev_e2e_blockchain_test.py — Phase 2 end-to-end proof harness
```
